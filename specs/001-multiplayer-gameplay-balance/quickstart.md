# Quickstart: 1v1 Asymmetric Multiplayer Gameplay & Balance Rules

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Contract**: [contracts/match-room-protocol.md](./contracts/match-room-protocol.md)

This guide validates the feature end-to-end once implemented. It does not include implementation
code — see `tasks.md` (generated by `/speckit-tasks`) for build-out steps.

## Prerequisites

- .NET 10 SDK installed (backend)
- Node.js 20 LTS installed (frontend build tooling)
- Repository dependencies installed (`backend/` .NET solution, `frontend/` npm workspace,
  `shared/` constants + codegen)
- Two browser windows/tabs available (to act as the two players) for manual runs, or Playwright's
  bundled browsers (`npx playwright install`, one-time) for automated runs

## Setup

```bash
# from repo root, once backend/frontend/shared exist
node shared/codegen/generate.js          # regenerates BalanceConstants.cs and balanceConstants.ts
                                          # from shared/balance-constants.json — run after any
                                          # balance-constant change, before building either side
dotnet run --project backend/src/MatchServer   # starts the ASP.NET Core / SignalR MatchHub server
npm install --prefix frontend
npm run dev --prefix frontend            # starts the Vite dev client, separate terminal
```

Open the printed frontend dev URL in two separate browser windows — the first to join (via
`JoinMatch()`) becomes Pac-Man (Runner), the second becomes the Ghost (Hunter), per the contract's
connection lifecycle.

To run the automated equivalent of every scenario below instead of driving it by hand:

```bash
npm install --prefix e2e
npx playwright test --config e2e/playwright.config.ts
```

`playwright.config.ts` starts the backend (`dotnet run`) and frontend (`vite dev`) as Playwright
`webServer` processes and opens one `BrowserContext` per role (Runner, Hunter) per test, so each
spec below can drive both players from a single test file without manual coordination.

## Validation scenarios

Each scenario below maps directly to acceptance scenarios in `spec.md` and to one Playwright spec
file under `e2e/tests/`; run them manually against the two connected clients, via the Playwright
suite above for full-stack automation, or via the `MatchServer.IntegrationTests` suite for a
backend-only equivalent (see `backend/tests/MatchServer.IntegrationTests/`).

### 1. Core match loop (User Story 1) — `e2e/tests/core-match-loop.spec.ts`

1. Join both clients; confirm the match timer starts counting down from 3:00 only once both roles
   are filled.
2. Drive the Hunter directly behind the Runner in a straight corridor with no turns; confirm the
   Hunter never closes the distance (spec US1 Scenario 3 — 95% vs. 100% base speed).
3. Let the Hunter catch the Runner in normal state 3 times; confirm the match ends immediately with
   `MatchEnded` reporting `winner: "Ghost"`, `reason: "LivesDepleted"`.
4. In a fresh match, collect every pellet on the map before the timer expires; confirm
   `MatchEnded` reports `winner: "Pacman"`, `reason: "PelletsCleared"`, regardless of time left.

### 2. Power Pellet role reversal (User Story 2) — `e2e/tests/frightened-state.spec.ts`

1. As Runner, eat a Power Pellet; confirm the Hunter's HUD speed value drops to 70% and its sprite
   switches to the flashing frightened visual within one state-sync tick.
2. During the first 3 seconds after that pickup, confirm the Hunter's Left/Right and Up/Down inputs
   are visibly inverted on screen (server-applied per the contract, not client-applied).
3. With ~2 seconds left on an active Frightened window, eat a second Power Pellet; confirm the
   Frightened countdown resets to a fresh 8.0s rather than adding to the remainder.
4. Catch the Hunter while Frightened; confirm it switches to eyes-only movement back to the Ghost
   House, is unavailable for ~5 seconds, and a `ScoreEvent` for 200 points arrives; catch a second
   Hunter in the same unbroken chain and confirm the next event is 400 points.

### 3. Vision & anti-camping (User Story 3) — `e2e/tests/vision-and-camping.spec.ts`

1. As Hunter, move within 6 tiles of the Runner (or into direct corridor line-of-sight); confirm the
   Runner becomes visible on the Hunter's client.
2. Move the Hunter out of range/behind walls from the Runner; confirm a `SonarPulse` message
   arrives roughly every 4 seconds with only a quadrant, never exact coordinates.
3. Park the Hunter within 3 tiles of an uncollected Power Pellet for more than 5 seconds without
   chasing; confirm the Hunter's speed drops an additional 15% (to 80% baseline) and the Runner's
   HUD shows the speed-boost indicator; move the Hunter away and confirm both clear.
4. Confirm the Runner's client never receives a fog-of-war restriction — the full map is always
   visible regardless of Hunter position.

### 4. Clarification-session edge cases — `e2e/tests/edge-cases.spec.ts`

1. Time out a match with the Runner having cleared exactly 70% of pellets and a strictly lower
   score than the Ghost's benchmark; confirm `winner: "Ghost"`.
2. Time out a match with the Runner at exactly 70% and an exactly tied score; confirm
   `winner: "Pacman"` (FR-023 tie-break).
3. Force a same-tick collision between a Runner Power-Pellet pickup and a Hunter normal-state
   catch; confirm the Runner's life is decremented (elimination precedence, FR-021) and that the
   resulting Frightened window only starts after the Runner's next respawn.
4. Close one browser tab mid-match; confirm the other client immediately receives `MatchEnded`
   with `reason: "Forfeit"` and the correct winner — no waiting period.

## Expected outcome

All scenarios above resolve deterministically and match the acceptance criteria in `spec.md`
exactly. Any scenario whose observed behavior differs from its spec citation is a defect against
this feature, not an acceptable implementation variance (Constitution Principle II).
